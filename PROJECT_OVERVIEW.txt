WHAT THIS REPOSITORY IS
--------------------------------------------------------------------------------
This is ARM's "Cortex-M3 DesignStart Eval" bundle (release CM3DesignStart-r0p0-
02rel0, 2017), used as the starting point for an in-house ARM Cortex-M3 SoC.
It is NOT a from-scratch SoC design — it is ARM's reference evaluation kit:
RTL for the SoC "uncore" (bus fabric, peripherals, memories) plus a licensed,
OBFUSCATED/encrypted model of the Cortex-M3 CPU core itself (ARM does not give
eval-kit users readable CPU RTL). Around this, the repo layers:
  - A cycle-based Verilog simulation testbench (run in ModelSim/Questa, VCS,
    or Xcelium) used to execute compiled firmware images against the SoC model.
  - A software tree (CMSIS device files, startup code, retarget/UART stdio,
    and ~20 test programs) that is compiled and loaded into that simulation.
  - A separate "boards/" bundle of prebuilt binaries for the physical MPS2+
    FPGA prototyping board (real hardware, not simulation).
  - Several optional/additional ARM IP bundles (m3designstart_iot, rtc_pl031,
    smm, trng) shipped alongside the core kit — all four are actively wired
    into the live build (see CONNECTIVITY below); only `boards/` is not.

In short: "SoC" here = Cortex-M3 core (opaque model) + CMSDK bus/peripheral
fabric + MPS2 FPGA-shield peripheral wrapper, all instantiated under a single
testbench top (tb_fpga_shield.v) that a Makefile-driven flow compiles and
simulates against one test program at a time.

END-TO-END FLOW: COMPILE AND RUN "hello"
--------------------------------------------------------------------------------
1. COMPILE THE FIRMWARE
   cd m3designstart/logical/testbench/testcodes/hello
   make
   -> arm-none-eabi-gcc compiles startup_CM3DS.s + hello.c + retarget.c +
      uart_stdout.c + uart_stdout1.c + system_CM3DS.c, links with
      software/common/scripts/cm3ds.ld, producing hello.o (ELF), then:
        objcopy -O binary  -> hello.bin
        objcopy -O verilog -> hello.hex
        objdump -S          -> hello.lst
   Default memory map (cm3ds.ld): FLASH at 0x00000000/64KB, RAM at
   0x20000000/63KB — standard Cortex-M vector-table-at-0 boot (word[0] =
   initial SP, word[1] = Reset_Handler address).

   ** NEW: the flash origin is now configurable from the command line **
   (as of commit c1e1d24, simplified in 2542e6d). cm3ds.ld now reads:
       FLASH (rx) : ORIGIN = DEFINED(FLASH_ORIGIN) ? FLASH_ORIGIN : 0x0,
                    LENGTH = DEFINED(FLASH_LENGTH) ? FLASH_LENGTH : 0x10000
       RAM  (rwx) : ORIGIN = DEFINED(RAM_ORIGIN)   ? RAM_ORIGIN   : 0x20000000,
                    LENGTH = DEFINED(RAM_LENGTH)   ? RAM_LENGTH   : 0xFC00
   and hello's makefile passes these through as `-Wl,--defsym=...` flags,
   driven by make variables (defaulting to the values above):
       make FLASH_ORIGIN=0x1000
   relinks hello to run from address 0x1000 instead of 0x0 (FLASH_LENGTH,
   RAM_ORIGIN, RAM_LENGTH are overridable the same way). Verify with:
       arm-none-eabi-objdump -h hello.o | head    # check .text VMA/LMA

2. COMPILE THE TESTBENCH
   cd ../../execution_tb
   make compile SIMULATOR=mti
   -> vlog compiles tb_fpga_shield.v and everything pulled in via tbench.vc
      (RTL + obfuscated CPU model) into a Questa "work" library. Default:
      simulator mti (Questa/ModelSim), toolchain gcc, DSM=no.

3. RUN
   make run TESTNAME=hello SIMULATOR=mti
   -> copies a CXDT.bin discovery image, converts hello.bin into
      flash_main.ini (16-bytes/line hex dump via `od`), runs vsim in batch
      mode, log -> mti_hello_run.log.
   -> Inside simulation: the code/flash memory model is
      u_ahb_blockram_128 (smm/logical/smm_common_fpga/verilog/
      ahb_blockram_128.v), instantiated inside m3ds_simple_flash.v (itself
      inside m3ds_user_partition.v) as the AHB target for TARGFLASH0. It
      preloads itself from flash_main.ini in an `initial` block at time 0
      (only active when `SIMULATION` is defined, which it is via
      `+define+SIMULATION=1` in tbench.vc — confirmed live, not dead code).

   ** NEW: where that preload lands is now also configurable, at run time,
   with no recompile needed ** (added this session, see FLASH LOAD ADDRESS
   below):
       make run TESTNAME=hello SIMULATOR=mti PLUSARGS="+FLASH_LOAD_ADDR=1000"
   loads flash_main.ini starting at simulated byte address 0x1000 in the
   256KB blockram instead of 0x0. Omit PLUSARGS for the old/default
   behavior (load at 0x0) — fully backwards compatible.

   -> CPU boots from address 0, jumps to Reset_Handler, SystemInit() runs,
      then main(). hello.c calls UartStdOutInit()/UartStdOutInit1() and
      prints via UartPutc()/Uart1Putc() -> CMSDK UART0/UART1 DATA register.
      cmsdk_uart_capture_ard.v (two instances now, one per UART) sniffs the
      TX line and echoes captured lines into the log with timestamps.
      Sending byte 0x04 (EOT) ends the simulation.

4. PASS/FAIL DETERMINATION
   `make runall` greps each test's run log for the literal string
   `** TEST PASSED **` (execution_tb/Makefile). hello.c currently has this
   commented out (see KNOWN ISSUES) — `make runall`/any log-grep check will
   report hello as FAILED even though the simulation runs cleanly.

FLASH LOAD ADDRESS — compiling AND running at a non-default memory location
--------------------------------------------------------------------------------
Two independent, paired knobs now exist for relocating where code lives,
one on each side of the compile/run boundary:

  COMPILE TIME (choose where the firmware is LINKED to run):
    cd m3designstart/logical/testbench/testcodes/hello
    make FLASH_ORIGIN=0x1000 [FLASH_LENGTH=0x10000] [RAM_ORIGIN=0x20000000] [RAM_LENGTH=0xFC00]
    Verify: arm-none-eabi-objdump -h hello.o   (look at .text's VMA/LMA)

  RUN TIME (choose where the SIMULATOR PLACES the compiled bytes):
    cd ../../execution_tb
    make run TESTNAME=hello SIMULATOR=mti PLUSARGS="+FLASH_LOAD_ADDR=1000"
    (hex byte address, must be 16-byte aligned, must be within
    0x0-0x3FFFF — the blockram_128's decoded 256KB window)

  These two values MUST MATCH for the loaded image to make sense — the
  linker origin controls what addresses the compiled code *believes* it's
  at (branch targets, data pointers); the plusarg controls *where the
  simulator physically drops the bytes*. Mismatch = code executing from
  the wrong place relative to its own internal address references.

  HOW TO VERIFY THE ADDRESS ACTUALLY TOOK EFFECT — three levels, cheapest
  first:
    1. Log message (always sufficient for day-to-day use): after `make run`
       with a plusarg given, grep the run log:
           grep "FLASH:" mti_hello_run.log
       prints `FLASH: loading flash_main.ini at offset 0x00001000` if
       accepted. Nothing is printed when no plusarg is given (default,
       silent, address 0x0). An invalid address (unaligned or out of
       range) instead prints an `ERROR:` line and the simulation
       immediately `$finish`es — that itself is confirmation the check is
       working.
    2. Direct memory inspection (for real proof the bytes landed correctly):
       run vsim interactively/batch against the already-compiled work
       library and `examine` the blockram directly, e.g.:
           vsim -c -64 +FLASH_LOAD_ADDR=1000 tb_fpga_shield \
             -do "run 0; examine -radix hex /tb_fpga_shield/u_fpga_top/u_fpga_system/u_user_partition/u_m3ds_simple_flash/u_ahb_blockram_128/BRAM0[256]; quit -f"
       (index = byte_address >> 4, since each BRAMn line is 16 bytes; index
       256 = byte address 0x1000). Compare against the linked binary's own
       bytes: `od -A x -t x1 -N 16 hello.bin`. `run 0` is required before
       `examine` — the preload happens in an `initial` block that hasn't
       executed until at least one delta-cycle/time-0 has elapsed.
    3. Full boot check: note that relocating FLASH_LOAD_ADDR away from 0x0
       does NOT relocate where the Cortex-M3 core fetches its boot vectors
       from — that's still hardware-fixed at address 0x0 (word[0]=SP,
       word[1]=Reset_Handler, read as data, not fetched as an instruction).
       If FLASH_LOAD_ADDR != 0x0 and nothing else occupies address 0x0, the
       CPU will not boot (MSP/PC both read as zero) — this is expected, not
       a bug in the relocation mechanism itself. Verified directly this
       session: relocating hello to 0x1000 places its bytes correctly
       (confirmed via BRAM examine) but produces no UART output, because
       address 0 is empty. A working two-stage relocated boot needs either
       something valid still at address 0x0 (e.g. ARM's own
       software/common/bootloader/bootloader.c pattern — see KNOWN ISSUES,
       currently non-functional in this SoC build) or a from-scratch
       trampoline; that is a separate, bigger piece of work from the
       load-address mechanism itself.
