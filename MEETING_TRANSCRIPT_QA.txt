THREAD A — BOOT LOADER / VECTOR TABLE RELOCATION
================================================================================

Q-A1. "Why doesn't putting a jump instruction at address 0 work to redirect
      the CPU to a bootloader?"
MEETING ANSWER: The mentor explains: whatever is at address 0 is read AS A
      VALUE by the CPU (taken as the initial stack-pointer value), not
      fetched and executed as an instruction — so encoding a "jump" there
      does nothing; the hardware boot sequence doesn't give you a chance to
      execute anything before that value is consumed.
PROOF (verified against this repo):
      m3designstart/software/cmsis/Device/ARM/CM3DS/Source/GCC/
      startup_CM3DS.s, lines 88-90:
          .long   __StackTop        /* Top of Stack   */  <- word[0]
          .long   Reset_Handler     /* Reset Handler  */  <- word[1]
      This is the standard ARMv7-M vector table: on reset, the CPU
      hard-wires two actions — load word[0] into the Main Stack Pointer,
      then load word[1] into the Program Counter (with a branch). Neither
      action fetches an instruction from address 0; both simply read a
      32-bit data value. The mentor's answer is architecturally correct.

Q-A2. "Does the boot process differ for Cortex-M4? / Is M0+ different (open
      source)?"
MEETING ANSWER: "True — M0+, as far as I know, is open source code," with
      the mentor noting the exact functional difference wasn't recalled
      precisely and one team member (Pranav) had looked at RISC-V for
      comparison as "just additional exploration."
PROOF: Partially confirmed, partially not verifiable from this repo. This
      repo's Cortex-M3 core (cortexm3_model/) is confirmed licensed and
      obfuscated (see PROJECT_OVERVIEW.txt CONNECTIVITY section) — not
      readable RTL, consistent with "M3 code is encrypted" said later in
      the same meeting (line ~42 of the source). Whether ARM's Cortex-M0+
      DesignStart tier ships as more open than M3 is an ARM licensing
      question outside this repo's scope — not something I can verify from
      the code here; treat the meeting's answer as informal recollection,
      not confirmed fact.

Q-A3. "First, why does it read from address zero? Does it specifically read
      from zero?"
MEETING ANSWER: "Yes — because that address is hard-coded... the entire
      memory map has addresses assigned this way, per what we studied in
      the [ARM] document." Confirmed later (line ~641): "location 0 = MSP,
      location 4 = initial PC."
PROOF: Confirmed exactly. m3designstart/software/common/scripts/cm3ds.ld:
          FLASH (rx) : ORIGIN = 0x0, LENGTH = 0x10000
      and startup_CM3DS.s's vector table (see Q-A1) — word[0]=SP,
      word[1]=Reset_Handler, placed at the FLASH origin (0x0) by the
      linker. This is standard ARMv7-M architecture, not an SoC-specific
      choice, but this SoC's linker script does place it at the
      architectural default (0x0).

Q-A6. "The bootloader isn't working — what's the correct way to do this?
      Should the vector table itself move, or just where the Reset_Handler
      eventually jumps to?"
MEETING ANSWER: The mentor's guidance (paraphrased): don't change where the
      vector table/MSP lives — keep that at 0 — but arrange for the
      Reset_Handler (or code right after it) to jump to wherever the real
      application lives. The junior tried this and reports it still isn't
      working ("hangs / terminates"), suspecting "some small mistake."
PROOF — I traced the actual root cause in this repo, which the meeting did
      not reach: the specific mechanism `bootloader.c` uses (ARM's own
      reference file, present unmodified at
      m3designstart/software/common/bootloader/bootloader.c) is
      SYSCON->REMAP: it writes REMAP=0 to switch which physical flash bank
      answers address 0, then re-executes the SP/PC load in software
      (FlashLoader_ASM, reading word[0]/word[4] again from the now-
      remapped address 0). This is architecturally correct ARM design —
      but it CANNOT work in this specific SoC integration, because:
        - m3designstart/logical/m3ds_user_partition/verilog/
          m3ds_user_partition.v:926 — `mtx_remap` is hardwired to constant
          `3'b0`, not driven by the SYSCON register at all.
        - Same file, ~line 2046 — the `beetle_sysctrl` instance's
          `.REMAP()` output port is left completely UNCONNECTED (dangling).
      So writing SYSCON->REMAP from software changes a register bit that
      drives nothing; address 0 never actually gets remapped, and
      FlashLoader_ASM ends up re-reading the SAME unremapped vector table
      it just came from — consistent with the observed hang. This is a
      genuine gap in this SoC build (not present in ARM's full reference
      board), not a mistake in the junior's own code. See
      PROJECT_OVERVIEW.txt, KNOWN ISSUES #4, for the same finding.
      Practical alternative (not yet tried by the team, per the
      transcript): SCB->VTOR-based relocation instead of REMAP — point the
      NVIC at a new vector table already resident in RAM/flash, no
      hardware remap wiring required. Untested in this repo; flagged as a
      forward-looking option, not a confirmed fix.

PROOF: This is the standard, textbook-correct answer for crossing an

Q-B3. "During oversampling, how many times is a value taken before
      deciding, and what happens if it changes mid-sample?"
MEETING ANSWER: 3x oversampling with majority vote, sampled at the middle
      of the bit period: 16 clock ticks per bit; after the start-bit
      falling edge, count 8 ticks to reach the middle, then take 3
      consecutive samples and use the majority value as the final sampled
      bit — repeated every 16 ticks.
PROOF: This is the standard UART 16x-oversampling + 3-sample-majority
      receive technique (used broadly in industry, including ARM's own
      PL011/CMSDK UART designs). Internally consistent and correctly
      explained by the junior; no contradiction found. Not independently
      re-derivable from this repo's files (the custom IP isn't here), but
      the explanation itself is textbook-correct.

Q-B4. "How many registers does it currently use? What's the sixth one, and
      what does the Peripheral ID (PID)/Component ID (CID) register
      actually do?"
MEETING ANSWER: 5 registers currently: Data, Status, Control, combined
      Interrupt-Status/Interrupt-Clear (shared offset), Baud-rate Divider.
      PID/CID not yet studied in depth by the juniors. The mentor then
      explains PID/CID's purpose at length: it lets software (a driver)
      identify which peripheral + hardware revision it's talking to at
      runtime, so the right register definitions/behavior get picked for
      that revision — critical when hardware gets revised across releases
      but old and new silicon must both be supported by one software
      stack.
PROOF: Register list matches exactly the register struct this repo's real
      CM3DS_MPS2.h defines for UART
      (m3designstart/software/cmsis/Device/ARM/CM3DS/Include/CM3DS_MPS2.h,
      CM3DS_MPS2_UART_TypeDef, ~line 174-185): DATA (0x000), STATE (0x004),
      CTRL (0x008), INTSTATUS/INTCLEAR (shared 0x00C, union), BAUDDIV
      (0x010) — five registers, exactly as described. The PID/CID registers
      the mentor describes ARE implemented in this repo's real UART RTL
      (cmsdk_apb_uart.v lines 85-96, 273-284): PID0-PID7 and CID0-CID3
      localparams at the standard ARM PrimeCell offsets (0xFD0-0xFFC),
      e.g. PID0=8'h21 (part number low byte), matching the mentor's
      description of a fixed, per-peripheral, per-revision identifier
      block exactly.

Q-B5. "Why would a 'TX buffer full' interrupt be useful to the CPU at all —
      shouldn't the CPU already know it just filled the buffer?"
MEETING ANSWER: Initially disputed and left UNRESOLVED in the meeting. The
      junior first defended "TX buffer full raises the interrupt" as
      correct per their reading of the spec document (later revealed this
      reading was produced with Claude's help — see Q-B6). The mentor
      pushed back that this seems backwards from a common-sense CPU-usage
      perspective (the CPU wants to know when there's room to send more,
      not when it's already full). By the end, the junior self-identified
      a real limitation: "for TX-buffer-empty I don't have logic to raise
      an interrupt — that's why I confirmed it as 'full' there," i.e. the
      "full" reading may be compensating for a gap in the RTL rather than
      being the intended design.
PROOF — resolved using this repo's real UART as a reference: In
      cmsdk_apb_uart.v (the actual working IP this SoC uses), the TX
      interrupt-set condition is:
          line 626: intr_stat_set[0] = reg_ctrl[2] & reg_ctrl[0] &
                                        tx_buf_full & tx_buf_clear;
      i.e. it fires when the buffer WAS full AND is simultaneously being
      cleared (data just moved out into the transmit shift register) —
      in effect, a "buffer just became available again / ready for more
      data" event, not a raw "still full" level condition. This is the
      answer the mentor was steering toward: from the CPU's point of view,
      what matters is "you can send more now," and the real reference IP
      implements exactly that transition-based condition rather than a
      simple level check on "full." This strongly suggests the custom IP
      under review is indeed missing the correct transition/clear-based
      logic, exactly as the junior suspected in their final remark.

Q-B7. "This interrupt-status/clear register should be RW1C (write-1-to-
      clear), right? What access types does your generation script
      actually support — read-only, write-only, write-only-clear,
      read-write?"
MEETING ANSWER: The mentor identifies this as a likely BUG: the register
      is currently generated as plain R/W, when interrupt-status/clear
      registers should be RW1C — writing 0 must have no effect; writing 1
      clears; the bit can only ever be SET by hardware, never by a
      software write. Action assigned: check what access types the
      Python/SystemRDL-based generation script actually supports, and
      confirm/fix the spec so RW1C is used, then re-verify the generated
      RTL (e.g. with a small APB testbench).
PROOF — confirmed via this repo's real UART as the authoritative
      reference for what "correct" looks like: cmsdk_apb_uart.v line 43
      (register-map comment): `0x0C R/Wc intr_status/INTCLEAR`, and lines
      31-32: "[3] RX buffer overrun (write 1 to clear)", "[2] TX buffer
      overrun (write 1 to clear)". The actual clear logic
      (intr_stat_clear[1:0] = {2{write_enable0c}} & PWDATA[1:0], line 629)
      only clears bits where PWDATA has a 1 — writing 0 to a bit leaves it
      unchanged, exactly RW1C semantics. This validates the mentor's
      assessment: the reference/real IP genuinely uses R/Wc (RW1C) for
      this register, so if the custom IP's generator only supports plain
      RW here, that is a real, confirmed functional bug (software clearing
      one interrupt source could accidentally clear/miss another, or a
      spurious write could clear a real pending interrupt) — not a false
      alarm.

Q-B8. "Does bit-toggling in this status/control register affect the actual
      UART interrupt pins? Are TX-interrupt and RX-interrupt on separate
      pins, or OR'd into one?"
MEETING ANSWER: Initially recalled (incorrectly) as "I think there's a
      single interrupt pin only." Immediately self-corrected after actually
      re-checking: "TX interrupt, RX interrupt — there ARE two separate
      pins." Further clarified: the combined/aggregate interrupt bit is
      produced by logically OR-ing multiple sub-conditions.
PROOF: Confirmed exactly against the real reference IP, cmsdk_apb_uart.v
      lines 78-82 (port list) and line 659:
          output wire TXINT,    // Transmit Interrupt
          output wire RXINT,    // Receive Interrupt
          output wire UARTINT   // Combined interrupt
          assign UARTINT = reg_txintr | reg_rxintr | tx_overflow_intr
                            | rx_overflow_intr;
      So the real IP has THREE separate interrupt-related outputs per
      instance (TXINT, RXINT, plus overrun variants TXOVRINT/RXOVRINT are
      also separate pins) in addition to one combined UARTINT that ORs all
      four together — confirming the junior's corrected answer (separate
      pins exist) and the general OR-ing description, though the real IP
      actually has four sub-sources OR'd together, not just two.

Q-B9. "Can the baud divider be changed after enabling TX/RX, or must it be
      programmed before enabling? What's the correct order?"
MEETING ANSWER: The junior reports trying both orders and both "worked" in
      their ad-hoc testing, but had not tested changing BAUDDIV mid-
      transmission specifically. The mentor's guidance: order of
      programming matters — data and baud rate can be set in either order
      relative to each other, but the enable bits (TX/RX enable in CTRL)
      must always be written LAST, after both baud rate and any pending
      data are configured. The junior's actual approach (enabling first,
      then control, then baud) was identified as the INCORRECT order.
PROOF: Consistent with this repo's own software convention already in
      use — m3designstart/software/common/retarget/uart_stdout.c,
      UartStdOutInit(): `CM3DS_MPS2_UART0->BAUDDIV = 53;` (or 32, per
      recent local edits) is set BEFORE `CM3DS_MPS2_UART0->CTRL = 0x01;`
      (enable) — i.e. this codebase already follows the order the mentor
      describes as correct (baud rate before enable). No hardware
      interlock enforcing this was found in cmsdk_apb_uart.v itself — it's
      a software/programming-sequence convention, matching the meeting's
      framing that this is about correct programming practice, not a
      hardware-enforced rule.
